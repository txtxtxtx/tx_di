# tx_di_registry 插件设计解读

> 本文档解读 `tx_di_registry` 插件的设计思想、模块职责、数据流与使用方式，
> 帮助理解这个"服务注册/发现 + 配置中心"插件为什么这样设计、各部分如何协作。
> 使用配置/API 见 `README.md`。

---

## 一、插件定位

`tx_di_registry` 为 tx-di 生态提供**服务注册/发现**与**配置中心**两个能力，是微服务化的基础设施插件：

```
┌────────────────────────────────────────────────────────────┐
│                      业务应用（如 tx_admin）                 │
│  ┌─────────────┐  ┌──────────────┐  ┌────────────────────┐  │
│  │ AdminEndpoints│  │ 业务组件      │  │ 业务组件（热更新）   │  │
│  │ (端点提供者)  │  │ (需要找服务)  │  │ (需要读配置)       │  │
│  └──────┬──────┘  └──────┬───────┘  └────────┬───────────┘  │
└─────────┼────────────────┼───────────────────┼──────────────┘
          │ register        │ discover/订阅      │ get/listen
┌─────────▼────────────────▼───────────────────▼──────────────┐
│                     tx_di_registry 插件                      │
│  ┌──────────────┐  ┌──────────────┐  ┌────────────────────┐  │
│  │ EndpointRegistry│ │ ServiceRegistry│ │    ConfigCenter    │  │
│  │ (端点注册表)   │  │  (抽象接口)   │  │    (抽象接口)      │  │
│  └──────────────┘  └──────┬───────┘  └─────────┬───────────┘  │
│                           │  NacosServiceRegistry │ NacosConfigCenter │
│                           │  (nacos-sdk 官方实现) │ (nacos-sdk 官方实现)│
└───────────────────────────┼───────────────────┼──────────────────┘
                            │  gRPC 双工长连接   │
                     ┌──────▼─────────┐  ┌─────▼─────┐
                     │  Nacos 服务端    │  │ r-nacos   │
                     │  (注册中心+配置) │  │ (轻量替代) │
                     └────────────────┘  └───────────┘
```

**设计核心**：把"注册中心的具体实现（Nacos/未来 Etcd/ZooKeeper）"与"业务如何使用注册中心"解耦——
业务只依赖 `ServiceRegistry` / `ConfigCenter` 两个抽象接口，实现可替换。

## 二、模块结构与职责

```
tx_di_registry/src/
├── lib.rs             # 模块声明 + 公共 API re-export
├── config.rs          # RegistryConfig 配置组件
├── traits.rs          # 三个核心抽象接口（依赖倒置的关键）

    └── config_impl.rs    # NacosConfigCenter（官方 nacos-sdk）
```

## 三、核心抽象（traits.rs）—— 依赖倒置的根基

插件把注册中心能力抽象成 **3 个接口**，业务代码只依赖这些接口：

### 1. `ServiceRegistry` — 服务注册/发现
```rust
#[async_trait]
pub trait ServiceRegistry: Send + Sync {
    /// 注册服务（按实例的全部端点注册，nacos-sdk 自动心跳保活）
    async fn register(&self, instance: &ServiceInstance) -> AppResult<()>;
    /// 更新实例（内部 = 注销 + 重新注册）
    async fn update(&self, instance: &ServiceInstance) -> AppResult<()>;
    /// 注销服务
    async fn deregister(&self, instance_id: &str) -> AppResult<()>;
    /// 发现服务（拉取 + 按 ip 聚合为多协议端点）
    async fn discover(&self, service_name: &str) -> AppResult<Vec<ServiceInstance>>;
    /// 订阅服务变更（回调拿到最新实例列表）
    async fn subscribe(&self, service_name: &str, callback: Box<dyn Fn(Vec<ServiceInstance>) + Send + Sync>);
}
```

### 2. `ConfigCenter` — 配置中心
```rust
#[async_trait]
pub trait ConfigCenter: Send + Sync {
    async fn get_config(&self, data_id: &str, group: &str) -> AppResult<Option<String>>;
    async fn publish_config(&self, data_id: &str, group: &str, content: &str) -> AppResult<()>;
    async fn remove_config(&self, data_id: &str, group: &str) -> AppResult<()>;
    /// 长驻监听：配置变更时回调（实现方阻塞直到取消，调用方用 select 取消）
    async fn listen_config(&self, data_id: &str, group: &str, callback: Box<dyn Fn(String) + Send + Sync>);
}
```

### 3. `EndpointProvider` — 端点提供者
```rust
pub trait EndpointProvider: Send + Sync {
    fn get_endpoints(&self) -> Vec<ServiceEndpoint>;
}
```
业务应用实现它来**声明"我这个服务的入口在哪"**（HTTP 端口、gRPC 端口、注册 IP），
注册中心据此注册。这就是微服务化预留的"接入点"。

> **为什么这样设计**：业务不 import 任何 Nacos 类型；如果将来换 Etcd/ZooKeeper，
> 只需新增一个实现并替换 `NacosServiceRegistry`，业务代码零改动。

## 四、数据模型（model.rs）

```rust
pub enum Protocol { Http, Grpc }

pub struct ServiceEndpoint {
    pub protocol: Protocol,        // HTTP / gRPC
    pub ip: String,
    pub port: u16,
    pub metadata: HashMap<String, String>,  // 附加信息（如 protocol=grpc）
}

pub struct ServiceInstance {
    pub service_name: String,
    pub instance_id: String,               // 业务侧唯一 ID
    pub endpoints: Vec<ServiceEndpoint>,   // 一个实例可暴露多个协议端点
    pub healthy: bool,
    pub metadata: HashMap<String, String>,
}
```

**关键设计**：一个逻辑服务实例（`ServiceInstance`）持有**多个端点**（`endpoints`）。
这适配"一个进程同时暴露 HTTP:8888 + gRPC:50051"的常见形态——
注册时把每个端点注册为一个 Nacos 实例（同一服务名下），发现时再**按 ip 聚合**回多端点实例。

## 五、端点注册表（endpoints.rs）—— 与应用解耦的桥梁

```rust
pub fn register_endpoints(provider: Arc<dyn EndpointProvider>);  // 应用启动时注册
pub fn collect_endpoints() -> Vec<ServiceEndpoint>;              // RegistryPlugin 收集
```

- **全局注册表**：进程内保存所有注册的 `EndpointProvider`（支持多个）。
- **时序依赖**：`AdminPlugin`（`init_sort = i32::MAX - 100`）调用 `register_endpoints`，
  `RegistryPlugin`（`init_sort = i32::MAX - 50`）在更晚的 `app_async_init` 中 `collect_endpoints`
  并注册到 Nacos——保证"端点先注册、后收集"。

```rust
// tx_admin 示例（admin_api/src/nacos.rs）
impl EndpointProvider for AdminEndpoints {
    fn get_endpoints(&self) -> Vec<ServiceEndpoint> {
        vec![
            ServiceEndpoint { protocol: Protocol::Http, ip, port: http_port, .. },
            ServiceEndpoint { protocol: Protocol::Grpc, ip, port: grpc_port, metadata: {"protocol": "grpc"} },
        ]
    }
}
```

## 六、动态配置机制（dynamic_config.rs + config_watcher.rs）

这是"配置中心"能力的**应用侧落地**，让业务配置可以热更新：

### `DynamicConfig<T>` — 进程内动态配置容器
```
┌───────────────────────────────────────────┐
│ DynamicConfig<RateLimitConfig>            │
│  inner: RwLock<T>        ← 当前值（原子读写）│
│  version: AtomicU64      ← 版本号（变更递增）│
│  tx: watch::Sender<ChangeEvent>  ← 变更广播  │
└───────────────────────────────────────────┘
```
- `get()` / `read()`：读取当前配置（快照克隆 / 借用）
- `update(new_val)`：原子更新 + 版本号 +1 + 广播 `ConfigChangeEvent`
- `subscribe()`：返回 `watch::Receiver`，业务可 `while rx.changed().await` 做热更新

### `ConfigWatcher` — 连接远端配置中心与本地容器
- 在 `RegistryPlugin::app_async_run` 中启动，对每个订阅的 `(data_id, group)`：
  1. 首次 `get_config` 加载并记录
  2. `listen_config` 订阅变更（阻塞，`tokio::select!` 配合取消令牌可优雅退出）
  3. 变更回调目前是 **TODO**（打印日志），预留了"反序列化后更新对应 DynamicConfig"的位置

> **演进路线**：Nacos 配置变更 → ConfigWatcher 回调 → 反序列化 → `DynamicConfig.update()`
> → 订阅方收到 watch 通知 → 业务热更新。当前回调仅日志，接入点已就绪。

## 七、Nacos 实现（nacos/）—— 官方 SDK

### 为什么用官方 `nacos-sdk`（0.8）而不是 `nacos_rust_client`（0.3）
| 维度 | nacos-sdk（官方） | nacos_rust_client |
|------|-------------------|-------------------|
| 架构 | tokio + tonic gRPC 双工长连接 | actix actor + 独立线程 runtime |
| 错误处理 | thiserror 结构化，async Result | register 是 fire-and-forget（不查结果） |
| 生产功能 | 防推空、磁盘缓存应急启动、鉴权、OTel | 基础功能 |
| r-nacos 兼容 | 官方 CI 测试路径含 rnacos | 作者个人维护 |
| 生态契合 | tokio（tx-di 同生态） | actix（割裂） |

### `NacosServiceRegistry`（registry_impl.rs）
- **注册**：`batch_register_instance` 把一个实例的多个端点批量注册为 Nacos 实例，
  SDK **自动心跳保活**（无需手写心跳循环）
- **注销/更新**：内部维护 `instance_id → 已注册实例` 的 HashMap，`deregister` 逐实例注销，
  `update` = 注销 + 重注册
- **发现**：`get_all_instances` 拉取 → 按 `ip` 聚合为多端点 `ServiceInstance`
  （从 metadata `protocol=grpc` 判断端点协议）
- **订阅**：`NamingEventListener` 实现 → 事件回调聚合后投递给业务
- 客户端 `load_cache_at_start(true)`：Nacos 服务端不可用时可用磁盘缓存应急启动

### `NacosConfigCenter`（config_impl.rs）
- `get_config`：`ConfigNotFound` 归一化为 `None`
- `publish/remove_config`：直调 SDK
- `listen_config`：`add_listener` 订阅（SDK 后台驱动）+ `pending()` 阻塞（配合 ConfigWatcher 的 select）

## 八、插件生命周期（plugin.rs）

```
启动时序（init_sort 控制）：
┌─ RegistryConfig (init_sort=i32::MIN)      ← 配置加载
└─ 业务组件 (如 AdminPlugin, MAX-100)         ← 注册端点 register_endpoints
   └─ RegistryPlugin (MAX-50)
       ├── app_async_init：构建 Nacos 客户端（.await）
       │   └── collect_endpoints() → auto_register 注册自身
       ├── app_async_run：ConfigWatcher 启动配置监听（心跳由 SDK 自动）
       └── shutdown：deregister 显式注销（Handle::block_on；无 runtime 时降级心跳超时剔除）
```

- **Config 组件**：`RegistryConfig`（`#[component(conf)]`，`[registry_config]` 节）
- **Plugin 组件**：`RegistryPlugin` 承载生命周期；`enabled=false` 时跳过构建与注册
- **心跳**：官方 SDK 的 gRPC 双工长连接自动保活（`register` 后后台驱动），插件侧无额外心跳循环

## 九、端到端数据流示例

### 服务注册（启动时一次）
```
AdminEndpoints.get_endpoints()
  → register_endpoints(Arc::new(AdminEndpoints{8888, 50051}))
  → RegistryPlugin.app_async_init
  → collect_endpoints() → [HTTP:8888, GRPC:50051]
  → NacosServiceRegistry.register(ServiceInstance)
  → batch_register_instance(service_name, group, [ins_8888, ins_50051])
  → Nacos 记录 2 个实例（同一服务名下），SDK 后台自动心跳
```

### 服务发现（任意时刻）
```
业务：registry.discover("tx-admin")
  → get_all_instances("tx-admin", group, [], subscribe=true)
  → Nacos 返回实例列表 → 按 ip 聚合 → [ServiceInstance{endpoints:[HTTP,GRPC]}]
```

### 配置监听（常驻）
```
RegistryPlugin.app_async_run
  → ConfigWatcher.run
  → 对每个 (data_id, group)：首次 get_config + listen_config(阻塞)
  → Nacos 配置变更 → 回调（TODO: 反序列化 → DynamicConfig.update → watch 广播）
  → 取消令牌 → select 退出
```

## 十、使用方式速查

```toml
# config.toml
[registry_config]
enabled = false                    # 生产多实例开启；本地无 Nacos 保持 false
nacos_addr = "http://127.0.0.1:8848"
namespace = "public"
group = "DEFAULT_GROUP"
service_name = "tx-admin"
auto_register = true
```

```rust
// 1. 依赖 + linkme 注册（main.rs）
use tx_di_registry;   // 必须显式 use，否则组件被链接器优化掉

// 2. 业务实现 EndpointProvider 并注册（plugin.rs 早期阶段）
tx_di_registry::register_endpoints(Arc::new(AdminEndpoints::new(http_port, grpc_port)));

// 3. 服务发现（任意业务组件）
let registry: Arc<dyn ServiceRegistry> = app.inject();   // 或 DI 字段注入
let instances = registry.discover("tx-admin").await?;

// 4. 配置热更新（订阅 watch）
let dc = DynamicConfig::new(default_cfg, "rate_limit");
let mut rx = dc.subscribe();
tokio::spawn(async move {
    while rx.changed().await.is_ok() { /* 热更新业务配置 */ }
});
```

## 十一、生产注意事项 / 已知限制

1. **`enabled=false` 默认关闭**：无 Nacos 的本地/单机环境不影响启动
2. **`SERVICE_IP` 环境变量**：容器/多网卡场景必须显式指定注册 IP（默认 127.0.0.1 仅单机调试）
3. **nacos-sdk 写操作阻塞**：服务端不可用时 `register` 等会阻塞（SDK 语义），生产配快速失败+后台重试
4. **ConfigWatcher 变更回调是 TODO**：目前只打印日志，热更新链路的"反序列化→DynamicConfig"待接入
5. **gRPC 端口不应直接暴露公网**：注册后由网关/Nginx 转发，50051 仅内网
6. **tonic 双版本**：nacos-sdk 用 tonic 0.14，与 admin_proto 的 tonic 0.12 共存（可接受）
7. **订阅回调是同步的**：`NamingEventListener::event` 在 SDK 内部线程回调，请勿在其中做阻塞操作
