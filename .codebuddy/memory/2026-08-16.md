  - 字符串值里的 `#` 不当作注释起始

## 操作日志/登录日志数据缺失修复

- 用户反馈：操作日志 trace_id 空、user_id 恒 0、request_method/request_url/user_ip 空；登录日志只有一条记录。
- 根因（数据库核实 + 代码定位）：
  1. `trace_id` 恒空 — `admin_api/src/plugin.rs` 消费端硬编码 `trace_id: String::new()`。
  2. `user_id` 恒 0 — `operate_log.rs` 的 `extract_user_info()` 在 `inner.call(req)` **之后**调用 `StpUtil::get_login_id_as_string()`，而 SaToken 的 task-local context 只在其 middleware 内部（inner.call 期间）有效，外层操作日志中间件已失效 → 永远拿不到 login_id。
  3. request 字段全空 — `CreateOperateLogRequest` proto **没有** request_method/request_url/user_ip/user_agent 字段；`OperateLogService::create_log` 也不接收；`OperateLog::with_request()` 从未被调用。
- 修复：
  - `admin_proto/protos/log.proto`：`CreateOperateLogRequest` 增加 4 个 optional string 字段（request_method/request_url/user_ip/user_agent）。
  - `admin_domain/src/system/log/service/mod.rs::create_log`：增加 4 个 `Option<String>` 参数并调用 `.with_request(...)`；同步更新 `service/tests.rs` 两个测试。
  - `admin_app/src/log/app_service.rs`：`OperateLogAppService::create_log` 透传这 4 个字段。
  - `admin_api/src/operate_log.rs`：重写中间件 — `OperateLogLayer::new(tx, token_name)`；在调用 `inner` 前从 Header/Cookie 提取 token（`extract_token`），inner 返回后用 `StpUtil::get_login_id(&TokenValue)` + `get_token_info` 显式查询用户信息（替代失效的 `extract_user_info()`）；`OperateLogEntry` 增加 `trace_id` 字段（`tx_common::id::next_id()` 生成）。
  - `admin_api/src/plugin.rs`：`OperateLogLayer::new(tx, sa_conf.token_name.clone())`；消费端填充 trace_id/request_method/request_url/user_ip/user_agent；写入失败打 warn。
  - `admin_app/src/auth/app_service.rs::login`：认证失败也记录登录日志（result=0），不再静默返回。
- 验证：`cargo check -p admin_api -p admin_app -p admin_domain -p admin_proto` 通过；`cargo test -p admin_domain --lib system::log` 24 passed。
- 遗留：sa-token task-local context 机制（`SaTokenContext::scope` 只覆盖中间件内部）是外层中间件无法用 `StpUtil::get_login_id_as_string()` 的根因，后续若有其他外层中间件需要用户信息应复用「提取 token → 显式查询」模式。

## 部门 ID 序列化修复（JS 精度丢失）

- 用户反馈：分配部门时前端 `deptIds` 是数字 `[82362011924697090]`，会被截断（JS Number 安全整数上限 2^53），应为 string。
- 根因：`list_depts` HTTP 接口直接返回 **domain 值对象 `DeptTreeNode`**（`admin_domain/src/identity/department/model/value_object.rs`），其 `id/parent_id/leader_user_id: u64` 没有 `serde_as` 注解，JSON 序列化为数字 → 前端 `el-tree` 的 `node-key="id"` 拿到被截断的数字 → `getCheckedKeys` 返回数字数组 → 提交 `deptIds` 数字被截断。
- 对照：`MenuTreeNode`（menu 域）已用正确模式（`#[serde_as]` + `DisplayFromStr` + `camelCase`），`DeptTreeNode` 漏了。
- 修复：给 `DeptTreeNode` 加 `#[serde_as]` + `#[serde(rename_all = "camelCase")]`，`id/parent_id` 用 `serde_with::DisplayFromStr`，`leader_user_id: Option<u64>` 用 `Option<DisplayFromStr>`（None → null，符合前端 `string | null`）。
- 注意：`DeptTreeNode` 是 domain 层值对象，直接作为 HTTP 响应体返回（不走 proto），因此 domain 层必须自带 serde_as（domain 已有 serde_with 依赖）。
- 验证：`cargo check -p admin_domain -p admin_app -p admin_api -p admin_infra` 通过；`cargo test -p admin_domain --lib identity::department` 28 passed。
- 检查结论：其余 HTTP 接口均返回 proto 类型（已带 FlexibleDisplayFromStr），无同类问题。
