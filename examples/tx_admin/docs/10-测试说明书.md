## 2. 测试策略总览

### 2.1 测试金字塔

本项目采用经典金字塔，**越底层用例越多、执行越快**：

```
                ┌──────────────┐
                │   E2E/生产   │  少量、慢、全链路（HTTP+gRPC）
                │   冒烟回归    │  覆盖关键用户旅程
                ├──────────────┤
                │   集成测试    │  中等数量、中速（admin_app + 真实 SQLite）
                │  AppService   │  覆盖应用编排 + Repository 落库
                ├──────────────┤
                │   单元测试    │  大量、极快（admin_domain）
                │ 领域模型/服务 │  mock 仓库，覆盖业务规则
                └──────────────┘
```

### 2.2 分层映射

| 层 | 测试类型 | 测试位置 | 关键依赖 |
|----|----------|----------|----------|
| `admin_domain` | 单元测试 | `src/<子域>/{model,service}/tests.rs` | `mockall` 模拟 Repository trait |
| `admin_app` | 集成测试 | `tests/*_test.rs` | 真实 toasty 内存 SQLite（`sqlite::memory:`） |
| `admin_api` | 端到端测试 | `tests/*_e2e_test.rs` | 完整 App（`BuildContext` + `ins_run`）+ `reqwest` |
| `admin_api` gRPC | 集成测试 | `tests/grpc_auth_test.rs` | 需外部启动服务（见 5.3.3） |
| `admin_infra` | （间接覆盖） | 由 admin_app 集成测试穿透 | toasty ORM |
| `admin_macros` | 缺失 | 见第 7 章 | trybuild |
| `admin_proto` | 缺失 | 见第 7 章 | prost 派生测试 |

### 2.3 测试隔离原则

项目存在**进程级全局状态**（`linkme` 组件注册表、`ROUTER_REGISTRY`、`LAYER_REGISTRY`、sa-token 会话、登录限流桶），测试隔离须遵循：

1. **集成/E2E 测试文件之间天然隔离**：每个 `tests/*.rs` 是独立二进制、独立进程。
2. **单文件内共享 App**：用 `OnceCell` 缓存（`admin_api/tests/common/mod.rs`），避免重复启动。
3. **全局状态避免并行污染**：`cargo test` 并行时不同测试文件各自独立进程，无需加锁；但同一进程内多个 `#[tokio::test]` 若操作同一 sa-token 会话需注意 token 隔离。
4. **登录限流桶**：`/api/v1/auth/login` 桶容量仅 5，E2E 文件内登录总次数必须计数（见 5.3.2）。

## 3. 测试环境准备

### 3.1 工具链

| 工具 | 版本要求 | 说明 |
|------|----------|------|
| Rust | 1.75+（workspace edition 2024） | 见根 `Cargo.toml` |
| protoc | 无需手动安装 | `protoc_bin_vendored` 自动提供 |
| SQLite | 无需安装 | toasty 内置 |
| PostgreSQL / MySQL | 可选 | 多数据库回归时使用（见 3.3） |
| Redis | 可选 | sa-token `redis` feature / Job 分布式锁测试时使用 |

### 3.2 测试专用配置

E2E 测试使用**内存 SQLite + 关闭 Nacos + 随机端口**，配置模板见 `admin_api/tests/common/mod.rs` 的 `TEST_CONFIG`，关键点：

```toml
[toasty]
database_url = "sqlite://memory"   # 内存库，用例间自动隔离
auto_schema = true                  # 自动建表
migrate_on_start = false
max_pool_size = 1                   # 单连接：规避 SQLite 写锁并发问题

[job]
enabled = false                     # 关闭 Job 调度器，避免干扰

[registry_config]
enabled = false                     # 关闭 Nacos

[web_config]
port = <运行时注入随机端口>
layers = [[5, "timeout"], [10, "api_log"], [100, "compression"], [10000, "cors"]]
```

> ⚠️ 配置节名使用宏实际读取的 key（`[toasty]`/`[log]`/`[sa_token]`），不是 `[xxx_config]` 后缀形式。

### 3.3 多数据库回归（可选）

生产可能切换 PostgreSQL / MySQL。多库回归流程：

1. 启动本地 PG/MySQL；
2. 覆盖测试环境变量 `DATABASE_URL`（若被测代码支持）或修改临时配置指向真实库；
3. 用 `auto_schema = true` 建表；
4. 运行 `admin_app` 集成测试套件。

> ⚠️ 注意：`admin_app/tests/common/mod.rs` 目前硬编码 `sqlite::memory:`，多库回归需提供可配置的 DB 工厂（属第 7 章缺口 G-7）。

### 3.4 环境变量

| 变量 | 用途 |
|------|------|
| `GRPC_PORT` | 覆盖 gRPC 端口（E2E 基座自动注入随机端口） |
| `CONFIG_PATH` | 覆盖配置文件路径（生产启动用） |
| `REDIS_URL` | sa-token Redis 会话（启用 `redis` feature 时） |
| `RUST_LOG` / `[log] level` | 日志级别 |

## 4. 测试执行指南

### 4.1 快速命令

```bash
# 全量（三层）—— 建议在项目根目录执行
cargo test -p admin_domain -p admin_app -p admin_api

# 仅领域层单元测试（最快）
cargo test -p admin_domain

# 仅应用层集成测试（串行，避免全局状态竞争）
cargo test -p admin_app -- --test-threads=1

# 仅接口层 E2E 测试
cargo test -p admin_api
```

### 4.2 分层执行明细

| 目标 | 命令 | 耗时参考 |
|------|------|----------|
| 全部 domain 单测 | `cargo test -p admin_domain` | ~10s |
| 单个子域 | `cargo test -p admin_domain user::` | 快 |
| 单个文件（集成） | `cargo test -p admin_app --test user_test` | ~30s |
| 单个用例 | `cargo test -p admin_app --test user_test create_user_success -- --exact` | 快 |
| 真实 DB 验证 | `cargo test -p admin_app --test real_db_test` | ~20s |
| 全链路工作流 | `cargo test -p admin_app --test workflow_test` | ~10s |
| E2E 冒烟 | `cargo test -p admin_api --test health_smoke_test` | ~15s（含启动） |
| 全部 E2E | `cargo test -p admin_api` | ~1~2min |
| gRPC 认证 | 见 5.3.3（需先启动服务） | 手动 |

### 4.3 串行执行的原因（重要）

`admin_app` 集成测试共享真实 SQLite 与 toasty 全局 `ModelSet`，**并行跑会出现写锁/模型重复注册竞争**：

```bash
cargo test -p admin_app -- --test-threads=1
```

`admin_domain` 单测全部用 mock，可放心并行。

### 4.4 测试失败排查指引

| 现象 | 常见原因 | 排查 |
|------|----------|------|
| E2E 连接被拒 | 常驻 runtime 泄漏失败 / 端口被占 | 检查 `admin_api/tests/common/mod.rs` `wait_for_ready` 超时（默认 15s） |
| 登录 429 | 限流桶耗尽（桶容量 5） | 计数本文件登录次数；复用 `admin_token()` |
| 集成测试写库失败 | SQLite `database is locked` | 用 `--test-threads=1` |
| 组件未注册（404） | 插件 crate 被链接器优化 | 确认 `use admin_api;` 空导入存在 |
| gRPC 连接失败 | 服务未启动 / 端口不对 | 见 5.3.3 手动启动流程 |

## 5. 分层测试规范

## 5.1 领域层（admin_domain）—— 单元测试

### 5.1.1 测试结构与定位

每个子域（user/role/menu/department/config/dictionary/file/log）下有：

```
src/<子域>/
├── model/
│   └── tests.rs        # 聚合根、值对象：状态流转、业务规则、不变式
├── service/
│   └── tests.rs        # 领域服务：用 mockall 模拟 Repository，验证用例逻辑
```

另有集中测试点：`src/shared/model/value_object.rs`（软删除/审计字段）、`src/password/mod.rs`（Argon2id 密码哈希）。

### 5.1.2 必须覆盖的用例类型

| 类型 | 说明 | 示例 |
|------|------|------|
| 状态机 | 聚合根状态合法流转 | 用户 `Active→Disabled→Active`、角色 `启用/停用` |
| 业务规则 | 不变式与前置校验 | 用户名唯一、邮箱格式、部门树无环、菜单树层级约束 |
| 值对象 | 构造/比较/转换 | `Sex`、`UserStatus`、`DeletedStatus` 的 `From`/`TryFrom` |
| 领域服务 | 用例编排 + 仓库交互 | `UserService::create_user`（mock 仓库断言调用参数与顺序） |
| 密码 | 哈希/校验/参数 | Argon2id 生成、错误密码拒绝、格式非法拒绝（11 个用例） |
| 删除语义 | 软删除 vs 硬删除 | `delete` 置 `DeletedStatus` 而非物理删除 |

### 5.1.3 编写规范（示例模式）

```rust
#[tokio::test]
async fn create_user_rejects_duplicate_username() {
    // Arrange: mock 仓库返回已存在用户
    let mut repo = MockUserRepository::new();
    repo.expect_find_by_username()
        .with(eq("dup".to_string()))
        .times(1)
        .returning(|_| Ok(Some(user_fixture())));
    let svc = UserService::new(Arc::new(repo));

    // Act
    let result = svc.create_user(CreateUserCommand { username: "dup".into(), ..Default::default() }).await;

    // Assert
    assert!(matches!(result, Err(AppError::Business(..))));
}
```

要求：**每个业务规则至少一条失败路径**；mock 用 `.times(N)` 显式断言调用次数；断言业务错误码而非字符串。

### 5.1.4 现状规模

约 **382 个**用例，覆盖 8 个子域 model + service。**缺口**：`file/model`、`log/model` 等个别聚合根状态流转深度不足；无属性化测试（`proptest`）覆盖字符串边界。

### 5.2.3 断言规范（六维度）

参照 `user_test.rs::create_user_success` 的成熟模式，每个写操作用例按六个维度断言：

1. **返回值正确性** —— 逐字段 `assert_eq!`
2. **持久化正确性** —— 通过查询 API 回查，验证落库字段与返回值一致
3. **默认值** —— 断言自动生成值（ID>0、状态默认、空列表、None 字段）
4. **审计追踪** —— 仓库直查 raw model，验证 `creator/updater/create_time/deleted`
5. **业务规则** —— 独立失败用例（重复、非法、越权）
6. **副作用** —— 关联表变更（角色绑定、部门绑定）

## 5.3 接口层（admin_api）—— 端到端测试

### 5.3.1 E2E 基座 `tests/common/mod.rs`

- 启动**完整 App**：`BuildContext::with_config(TEST_CONFIG)` → `build()` → `ins_run()`
- **常驻 runtime**（`Box::leak`）：Web 服务器绑定在该 runtime 上，跨测试存活（防止 `#[tokio::test]` runtime 销毁连带杀掉 server）
- 随机端口 + `GRPC_PORT` 环境变量注入 + `/health/live` 轮询就绪
- `admin_token()`：互斥锁串行化首次登录，进程内只真正登录一次（规避限流桶）

### 5.3.2 HTTP E2E 测试文件

| 文件 | 覆盖 | 用例数 |
|------|------|--------|
| `health_smoke_test.rs` | `/health`、`/health/live`、`/health/ready`、登录冒烟、401 | 4 |
| `auth_e2e_test.rs` | 登录成功/失败、user_info、登出后 token 失效 | 5 |
| `rbac_e2e_test.rs` | 角色/菜单/部门 CRUD、树、层级删除保护、鉴权 | 21 |
| `user_e2e_test.rs` | 用户 CRUD、分页、状态、改密、角色部门分配 | 14 |

**限流预算约束**：`/api/v1/auth/login` 桶容量 5。每个 E2E 文件内登录次数需计数（`auth_e2e` 已注明 4 次预算），新增登录类用例前必须复核。

**E2E 断言约定**：
- 业务错误走 HTTP 200 + `code` 业务码；认证失败 HTTP 401（sa-token 拦截器直接返回，空 body）
- `u64` 字段（id/userId 等）JSON 序列化为字符串，用 `extract_id()` 兼容提取
- 分页请求顶层 `page`+`pageSize`；分页响应 `Page{list,page,size,total}`
- 并行用例用 `unique_suffix()`（时间戳纳秒）生成唯一 code/name/username

### 5.3.3 gRPC 测试（grpc_auth_test.rs）—— 手动流程

⚠️ **当前 gRPC 测试依赖外部运行的服务**（连接固定 `127.0.0.1:50051`），不随 `cargo test` 自动通过。执行流程：

```bash
# 1. 启动服务（另一个终端）
cargo run -p admin_api

# 2. 运行 gRPC 测试（单独，不与其他测试混跑）
cargo test -p admin_api --test grpc_auth_test
```

覆盖：gRPC 登录成功、错误密码返回 `Unauthenticated`、携带 token 获取用户信息、登出。

> **改进建议（属缺口 G-2）**：gRPC 测试应改为自动启动服务器（复用 `common::server()` 的常驻 runtime 模式 + 注入随机 gRPC 端口），并从 `BuildContext` 拿到 App 后 `tokio::spawn` 启动 tonic server，实现全自动。

### 5.3.4 内联单元测试

- `src/interfaces/grpc/auth_interceptor.rs` —— 3 个用例：`extract_bearer_token` 正常/缺失/格式错误，已覆盖。

## 11. 测试用例编写规范

### 11.1 命名

- 集成/E2E 用**行为式**小写下划线：`create_user_success`、`delete_menu_has_children_rejected`
- 领域单测可用 `mod tests` + 同类命名
- 断言描述用中文注释说明验证维度（参照 `user_test.rs` 的六维度注释风格）

### 11.2 断言

- 优先具体断言：`assert_eq!(x, expected)` 而非 `assert!(x)`；集合用 `assert!(v.contains(..))`
- 错误路径断言业务码/枚举变体，不依赖字符串消息（gRPC `err.rs` 字符串匹配是已知脆弱点）
- E2E 断言约定遵循 5.3.2（HTTP 200+code / 401 空 body / u64 字符串化 / 分页结构）

### 11.3 隔离与幂等

- 每个用例创建**唯一**实体（时间戳后缀），可并行、可重复运行
- 集成测试每个用例用独立内存库（`create_db_plugin()` 每次新建）——天然隔离
- 不依赖用例执行顺序；不依赖 seed 之外的数据状态（seed 由 `auto_schema=true` 保证）

### 11.4 异步与全局状态

- 所有异步测试用 `#[tokio::test]`（默认 current_thread，够用）
- 不要在任何测试的局部 runtime 里启动长期服务（会随 runtime 销毁被杀）；参考 E2E 基座的**常驻 runtime + leak** 模式
- 涉及全局注册表/限流桶的用例，单文件内注意共享状态预算

### 11.5 慢/特殊用例

- 需要人工环境或用例标记 `#[ignore]`，并写入 README 说明触发方式（gRPC 用例当前即此模式）
- 性能类基准进 `benches/`（criterion），不进普通测试

## 12. 缺陷管理与回归策略

### 12.1 缺陷 → 用例闭环

每个已修复 bug 必须附带一条**回归用例**（复制失败现场 → 修复 → 用例通过 → 入库）：

1. 复现：写出能稳定复现的最小用例（优先集成/E2E 层，贴近真实路径）
2. 修复：实现修复
3. 验证：用例通过，且全量测试无回归
4. 沉淀：用例保留在对应 `tests/`，注明关联缺陷编号

### 12.2 回归范围建议

| 变更类型 | 必跑回归 |
|----------|----------|
| 领域规则修改 | `admin_domain` 全量 + 相关 app 集成 |
| AppService 改动 | `admin_app` 串行全量 |
| 路由/鉴权/中间件 | `admin_api` E2E 全量 |
| proto 变更 | admin_proto 序列化测试 + 全部 E2E（DTO 变化影响双协议） |
| Repository/Schema | `admin_app` 全量 + `real_db_test` |
| 插件（sa-token/toasty/job） | 受影响模块集成 + E2E |

### 12.3 缺陷统计口径

| 指标 | 定义 |
|------|------|
| 逃逸率 | 生产环境缺陷数 / 测试期缺陷总数，目标 < 5% |
| 回归率 | 修复引入的新缺陷占比，目标 < 2% |
| 修复附测率 | 附回归用例的修复占比，目标 100% |
