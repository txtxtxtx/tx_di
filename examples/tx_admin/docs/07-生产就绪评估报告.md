# tx_admin 生产就绪评估报告

> **评估日期**: 2026-08-06
> **评估对象**: `examples/tx_admin`（admin_api / admin_app / admin_domain / admin_infra / admin_proto / admin_macros / web）
> **评估范围**: 暂不考虑 gRPC 微服务拆分（gRPC 已为后续预留位置，见 §4）；重点评估当前单体能否直接生产部署、能否水平扩容。

---

## 一、总体结论

**当前状态：功能完整、可编译、可测试通过的"高质量示例/原型"，但尚未达到生产可用标准。**

| 维度 | 评级 | 说明 |
|------|------|------|
| 编译 | ✅ 通过 | `cargo check -p admin_api` 通过，无编译错误 |
| 测试 | ✅ 通过 | `admin_app` 集成测试约 101 个全部通过（含真实 SQLite 集成测试）；`admin_domain` 单测通过 |
| 功能完整度 | 🟡 中高 | 12 个业务模块 CRUD 齐全，HTTP + gRPC 双协议 |
| 架构质量 | ✅ 较好 | DDD 四层清晰，domain 不依赖 infra，DI 原生注入 |
| 安全性 | 🟡 中 | 密码 Argon2id 优秀，但缺限流、token 存 localStorage、无安全头配置 |
| **可部署性** | 🔴 **差** | **配置路径硬编码，换机器即无法启动**（见 P0-1） |
| **可扩展性** | 🔴 **差** | 内存会话、无分布式锁、无事务、全量内存分页（见 §3） |
| **可观测性** | 🔴 差 | 只有日志，无 metrics / 链路追踪 / 健康检查 |

**一句话结论**：作为后台管理系统示例，工程质量是同类项目中较好的；但**当前版本不满足生产部署条件**，存在 5 个阻断级（P0）问题和 10+ 个高风险（P1）问题。其中配置硬编码是"一票否决"项——不改代码、换台机器就起不来。水平扩容则被内存会话、Job 无分布式锁、无健康检查三座大山阻断。

## 三、问题清单（按严重程度）

### 🔴 P0 阻断级 —— 不修复无法生产部署

| # | 问题 | 位置 | 影响 |
|---|------|------|------|
| P0-1 | **配置路径硬编码** | `admin_api/src/main.rs:32` 硬编码 `C:\a_me\proj\rust\tx_di\...`（本机为 `D:\proj\tx_di`） | **换机器/换目录无法启动**；无环境变量/命令行覆盖（tx-di-core `AppAllConfig::new` 仅从文件加载）。修复：读 `CONFIG_PATH` 环境变量 + 默认回退 `config/config.toml` |
| P0-2 | **会话为内存存储** | `admin_api/Cargo.toml:24`、`admin_app/Cargo.toml:20` 均 `features = ["memory"]` | 多实例部署时登录 A 实例、请求被转发到 B 实例即 401。**水平扩容首要障碍**。框架已支持 `redis` feature，但连接串目前只能走环境变量 `REDIS_URL`（插件 README 确认"尚未从 TOML 读取"） |
| P0-3 | **无事务管理** | 全局（AppService 层） | `create_user` = 建用户 + 设可选字段 + 绑角色 + 绑部门，每一步独立提交，中途失败留下脏数据；`bind_roles`/`bind_departments` 先删后插非原子 |
| P0-4 | **全量内存分页** | 所有 Repository 的 `find_page`（如 `admin_infra/src/user/repository.rs:110`）、`admin_app/src/job/app_service.rs:93` | 列表接口 `SELECT 全表` 到内存再 `filter().skip().take()`，`total` 用 `filtered.len()`。数据量上万即内存/网络/响应时间劣化，是慢查询和 OOM 隐患。toasty 支持 `offset/limit` 但未用 |
| P0-5 | **Job 调度无分布式锁** | `plugins/tx_di_job/src/comp.rs:421` `last_trigger: HashMap` 为进程内状态 | 多实例各自维护触发时间槽，**同一 cron 任务被 N 个实例重复执行**。需 Redis 分布式锁或"调度器单实例化" |

### 🟠 P1 高风险 —— 生产上线前必须处理

| # | 问题 | 位置 | 说明 |
|---|------|------|------|
| P1-1 | **无健康检查端点** | 全局 | 无 `/health`、`/health/live`、`/health/ready`。负载均衡器/r-nacos/K8s 无法探活。docs/06 方案已规划但未实现 |
| P1-2 | **gRPC 端口硬编码** | `admin_api/src/plugin.rs:42` `DEFAULT_GRPC_PORT=50051` | 未配置化，多实例/容器化时端口冲突；与 docs/06 的 `SERVICE_GRPC_PORT` 环境变量设计脱节 |
| P1-3 | **无登录限流/防暴力破解** | 全局 | 登录接口可无限尝试；无速率限制中间件（`tower_governor`/`axum-rate-limit` 等均未引入） |
| P1-4 | **Token 存 localStorage** | `web/src/api/request.ts:19` | XSS 可窃取 token。生产建议 HttpOnly Cookie（`is_read_cookie` 已支持）或配合 CSP |
| P1-5 | **无可观测性** | 全局 | 只有 tracing 日志。无 metrics（prometheus）、无 OpenTelemetry 分布式追踪、无统一 trace_id 透传（操作日志的 `trace_id` 字段恒为空字符串） |
| P1-6 | **路由无版本前缀** | `admin_api/src/interfaces/api/mod.rs:34` | 全部 `/api/*`，无 `/api/v1`。API 演进/兼容管理困难，也是未来拆微服务的障碍 |
| P1-7 | **无数据库迁移机制** | `admin_infra/src/plugin.rs` | `auto_schema=false` 时表结构完全靠人工维护；`auto_schema=true` 仅首次建表+种子。无迁移版本管理（类似 SQLx migrate / refinery），生产 schema 演进无流程 |
| P1-8 | **领域事件只收集不发布** | `admin_domain/src/shared/model/mod.rs` | `DomainEvent` 枚举约 40 个变体被聚合根收集，但全项目无 EventBus/Publish。事件驱动能力是"半成品"，若要做审计、通知、缓存失效等扩展无从下手 |
| P1-9 | **注册中心依赖不可用** | `plugins/tx_di_registry` | Nacos 后端为 TODO 占位。docs/06 微服务方案的"服务注册/配置中心"当前**无法落地**（需先补全该插件或自研 r-nacos HTTP 注册） |
| P1-10 | **相对路径依赖启动目录** | `config/config.toml` | `database_url = "sqlite:examples/tx_admin/data/tx_admin.db"`、`web_config.spa_apps` 指向 `examples/tx_admin/web/dist`、`file_config.base_path="./uploads"`、日志目录 `./logs` 均相对 CWD，服务化/systemd/容器下极易失效 |
| P1-11 | **操作日志静默丢失** | `admin_api/src/operate_log.rs:187` | 有界 channel（4096）满时丢弃日志仅 warn。审计类日志生产上不应丢弃，建议降级为同步写或落盘兜底 |
| P1-12 | **gRPC 错误映射靠字符串匹配** | `admin_api/src/interfaces/grpc/err.rs` | 通过错误文本包含"token/密码/权限"等关键词推断 `Status`，脆弱易错。proto 也无统一错误码 message |

## 四、gRPC 预留位置评估（用户关注点）

**结论：gRPC 的"骨架"已就位，可平滑演进为微服务通信层，但还差"最后一公里"配置化与配套。**

### ✅ 已就位（无需返工）
- `admin_proto`：13 个 `.proto` 文件，16 个 Service（Auth/User/Role/Menu/Dept/Config/Dict/Log/File/FileConfig/Monitor/Tool/Job/JobLog），消息结构完整，`protoc_bin_vendored` 免安装编译
- `tonic` server 已注册全部 13 个业务服务（`admin_api/src/plugin.rs:117`）
- Tower `AuthLayer` gRPC 认证拦截器（token 校验 + RBAC），与 HTTP 共用 sa-token 会话
- **HTTP 与 gRPC 共享同一套 AppService**（`DiComp<T>` 注入），业务逻辑天然复用 —— 这是拆微服务时最值钱的资产：proto DTO 与业务用例已解耦
- proto 生成的 DTO 同时驱动 HTTP JSON 序列化（`serde` 派生），双协议一套模型

### ❌ 缺失/需补（为微服务化预留的缺口）
1. **gRPC 端口配置化**（P1-2，见上）：`DEFAULT_GRPC_PORT` 硬编码 → 改为从配置/环境变量读取
2. **gRPC health / reflection 服务**（P2-4）：`tonic_health` 探活 + `tonic_reflection` 客户端调试
3. **proto 统一错误码**：当前靠字符串匹配转 `Status`，微服务间错误传播需标准化
4. **跨服务链路追踪**：gRPC 拦截器需透传 trace context（与 P1-5 一并解决）
5. **服务间鉴权升级**：当前 Bearer token（sa-token）适合网关代理；服务直连场景需考虑 mTLS / 服务间凭证
6. **proto 分页/查询参数统一**（P2-3）：为服务间调用对齐契约

### 演进建议
- 短期（保持单体）：把 gRPC 端口配置化 + 补 health/reflection，HTTP 与 gRPC 并存作为能力出口
- 中期（服务化）：当需要拆分时，优先拆"无状态、易横向扩展"的域（如 dict/config/log），通过 gRPC 与主服务交互；`tx_di_registry` 服务发现需先落地（当前为占位）
- 网关策略：对外统一走 HTTP（现有 `/api`），内部 gRPC；避免直接暴露 50051 到公网
